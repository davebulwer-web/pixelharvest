# Pixel Harvest — art specification

**This file is the defence against style drift.** Every Pixellab generation uses the spec
and prompt template below, unchanged, for the life of the project. Consistency comes from
mechanical reuse of the same words and the same reference images — not from writing a
better prompt each time.

---

## Locked specification

Do not change these after Stage 1 without an entry in `DECISIONS.md`.

| Property | Value |
|---|---|
| Tile size | 16 × 16 px |
| Character cell | 48 × 48 px — the figure itself is ~16 × 37, centred, with padding around it. Pixellab's smallest practical character size; the padding is useful later for tool-swing frames that reach beyond the body |
| Character directions | 4 — no diagonals. Pixellab exports them in compass order **south, west, east, north**, which maps to down, left, right, up |
| Character animations | idle, walk, use-tool |
| Perspective | Top-down three-quarter, as Stardew Valley — ground seen from above, objects drawn from the front |
| Light source | Top-left, consistently |
| Outlines | Dark selective outline; no outline where a shape meets its own shadow |
| Palette | Whatever `art/palette.png` holds — see below |
| Dithering | None. Flat colour areas with hard-edged shading |
| Background | Transparent for sprites; opaque for tilesets |

## Palette — derived, 41 colours

`art/palette.png` is the single source of truth. It is **derived from the art**, not
imposed on it: the union of every colour present in the project's assets, regenerated by
`make_palette.py` and read directly by the asset checker.

It began life as a hand-written 32-colour guess called Harvest 32, written before any art
existed. That guess contained no skin tones at all, so the first real character could
never have matched it — ten of its nineteen colours were close and nine were well off.
Degrading good art to satisfy a guess would have been the wrong trade, so the palette was
rebuilt from what the art actually uses. It came out at 33 colours, barely larger than the
guess, and every asset now sits exactly on it.

The discipline is unchanged, only better founded. New art that introduces colours shows up
as off-palette in the checker. That is the signal to make a deliberate choice — accept the
colours and regenerate the palette, or correct the asset. What it must never be is silent.

## Prompt template

Paste this before the subject description, every single time:

> 16-bit top-down three-quarter farming game sprite, Stardew Valley style, flat colours
> with hard-edged shading, dark selective outline, light source top-left, no dithering,
> no anti-aliasing, limited earthy palette of muted greens browns and warm accents,
> transparent background. Subject:

Then the subject, kept short and concrete. Good: *"young farmer in a straw hat and blue
dungarees, walking south"*. Bad: *"a charming farmer character full of personality"* —
Pixellab has nothing to do with adjectives like charming, and they vary the output.

## Reference images

Two reference images, created once and reused forever:

- `art/palette.png` — the 32-colour swatch. Supply as a palette or style reference.
- `art/reference.png` — the first approved character sprite. From Stage 1 onward this is
  the style anchor for every subsequent generation.

**For seasonal tilesets, always use image-to-image from the base tileset**, never a fresh
prompt. Four seasons generated independently will not match; four seasons derived from one
base will. See `DECISIONS.md` 005.

## Who does what

- **Dave** judges whether an asset looks good. That's taste, and it isn't Claude's call.
- **Claude** handles the mechanics: constructing prompts from the template, checking
  dimensions and frame counts, extracting each PNG's palette and flagging any colour
  outside Harvest 32, and recording every generation below.

Claude can verify an asset with a short script — image size, frame grid, transparency,
and the exact set of colours used. That's the part worth automating: catching drift is more
reliable than hoping to avoid it.

## How generations get made

> **Superseded by DECISIONS 019:** generation now goes through Pixellab's API from a
> cloud environment that can reach it. The routes below remain as fallbacks.

Pixellab isn't in Claude's connector directory, so there's no one-click connection. Two
routes, either fine:

1. **Pixellab's MCP server** — added by hand as a custom connector using the details on
   `pixellab.ai/vibe-coding`. Claude can then generate directly and verify immediately.
   Note that Claude's own sandbox can't reach `api.pixellab.ai`, so a connector is the
   route, not API calls from code.
2. **Pixellab's web editor** — Dave generates using the template above and drops the PNGs
   into `assets/`. Claude then verifies them and reports anything off-spec.

Route 2 works perfectly well and needs no setup. Route 1 mainly saves round-trips.

Re-exporting with the walk cycle changed the cell size from 48 to 56 and the row layout
entirely, but **not a single colour** — the same 19 came back. That is a useful property
to know about Pixellab: adding animations to an existing character is colour-stable, so
the palette can be locked once a character is final without fear of later drift.

**How the 2026-11-14 batch was made, and why.** Every image went through Pixellab's v2 API
with `color_image` (or `target_palette`) set to `art/palette.png`, so all of it landed
exactly on the 33 colours and the palette did not grow. A crop's stages are drawn together
in one strip, not one image per stage: separately generated stages don't look like the
same plant. Crops carry **no soil of their own** (Dave's call) because the game already
draws tilled ground under them. pixflux costs one generation but refuses canvases under
32×32 in area, which is why icons come four to a strip; Pro Flash can do a single 16×16
but costs five. The whole batch, including tests and redos, was about 35 generations.

**Ready stages redrawn, 2026-11-14.** Dave found that some crops didn't look obviously ready.
The last frame of radish, potato and parsnip was redrawn in one pixflux strip (init =
the old ready frames, strength 100) with the harvest described as large and visible. The
green bean pods wouldn't show at 16px, so the whole bean sheet is now **80×32**, five
16×32 frames: a climbing vine whose ready stage is a tall, full vine on a stake (init =
the old sheet in the bottom half, strength 30). Taller frames need no code: `CropDef`
bottom-aligns its frames. 8 generations.

**Seasonal placeholders, 2026-11-14 (Stage 6).** Not Pixellab: recoloured by a script from
the spring placeholders, using only palette colours, so the atlas layout is identical.
`tilesets/ground_{summer,autumn,winter}_placeholder.png` (summer: brighter grass; autumn:
darker grass with fallen leaves, russet thicket; winter: snow, iced pond, snow-capped cliffs
and thicket) and `sprites/tree_{autumn,winter}_placeholder.png`. Still owed as real art:
the base ground tileset and tree (Stage 1 placeholders), then the three seasonal sets and
seasonal trees by **image-to-image from that base** — keep all nine atlas columns,
including the thicket in column 8.
